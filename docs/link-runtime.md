# Link 執行期與資源上限

## 公開介面

應用程式從 `pcan-link` 或 `pcan-kit` 根目錄匯入連線、設定、事件與控制代碼，
例如 `Link`、`LinkBuilder`、`LinkState`、`SubscribeConfig`、`ResponseSpec` 與
`CyclicConfig`。`LinkState` 供觀測，狀態變化透過 `state_watch()` 與 `events()` 取得。
重連行為由 `BackoffPolicy` 與 `LinkBuilder` 設定。

Link 的實作模組、狀態機輸入／動作、動作集、傳送閘門與抖動器實作均為內部細節，
不屬於公開 API。測試仍在內部直接驗證純狀態機；應用程式不需要驅動它。

## 責任分工

| 內部模組 | 責任 |
|---|---|
| `supervisor::machine` | 純狀態轉移，不持有時鐘、不執行 I/O |
| `supervisor::actions` | 執行開啟／關閉傳輸層、設定重放、計時與通知動作 |
| `supervisor::receive` | 分派接收幀、管理訂閱及交易表、統一健康狀態與溢位計數 |
| `supervisor` | 建立背景工作、選取事件與計時器、協調故障及關閉 |
| `control` | 訂閱、交易與週期項目的生命週期准入 |
| `router`、`transaction`、`cyclic`、`txqueue` | 分別管理訂閱、回應等待、週期排程及傳送背壓 |

接收狀態事件與定期健康查詢共用同一個狀態觀測入口。警告溢位僅在位元上升緣計數，
健康查詢不增加接收錯誤幀數。RX 靜默期限從連線建立完成起算，初次開啟耗時不算靜默。
關閉與斷線集中清理交易表，同步更新活躍交易數，避免關閉後仍顯示舊值。

## 控制資源預算

`LinkBuilder::control_capacity(n)` 為訂閱、交易與週期項目各配置獨立預算，
預設各 1024；零視為 1，過大的值截至 Tokio 信號量上限。三類互不占用彼此名額。

每個項目的建立命令、控制代碼與必要的背景項目共享同一名額。清理命令沿用原名額，
直到最後一個持有者釋放才歸還，涵蓋下列狀況：

- 尚未處理的建立命令：取消呼叫不會提前歸還名額；背景處理或丟棄命令後回收。
- 尚未領取的確認訊息：確認訊息持有控制代碼，丟棄時自動送清理命令。
- 使用中的項目：每個控制代碼占一個名額，訂閱溢位關閉或交易斷線也不會提前歸還。
- 待清理命令：`Drop` 不需要額外名額或非同步等待，滿載時仍能送出清理。
- 已完成但尚未釋放的週期控制代碼：仍保留名額，避免殘留更新與停止命令持續累積。
- `detach()` 項目：背景排程保留名額，直到項目結束或連線關閉。

命令數量由名額與每項目的合併規則共同限制。訂閱與交易不會因反覆取消而持續
累積失去名額追蹤的清理命令；週期更新保留每項目最多一筆待處理喚醒，
觸發次數封頂於 `max_burst`。`stop()` 送出停止命令後立即停用 Drop 的自動停止，
即使等待確認時被取消，也不會重複送出停止命令。

| 限制 | 滿載結果 |
|---|---|
| 訂閱／週期生命週期預算 | `Error::ControlQueueFull { capacity }` |
| 交易生命週期預算 | `TransactionError::ControlQueueFull { capacity }` |
| 活躍交易數 `max_in_flight_transactions`，預設 64 | `TransactionError::TooManyInFlight { limit }` |
| 週期待處理新增命令 `MAX_PENDING_CYCLIC_ADDS`，固定 256 | `Error::ControlQueueFull { capacity: 256 }` |
| 傳送資料、訂閱接收緩衝及交易結果 | 各自依既有容量與溢位設定處理 |

這些預算限制項目數與命令數，不是整個行程的位元組總額；呼叫端仍應合理設定
單一訂閱緩衝、交易結果數與其他容量。連線已關閉時，新增操作回報 `Closed`。
名額不足時先釋放不再使用的控制代碼，並讓背景工作完成清理後再重試。

## 回歸驗證

`pcan-link/tests/control.rs` 驗證背景尚未執行時的註冊洪峰與取消、清理回收、
各類預算隔離、溢位關閉、有限次 detach，以及關閉後的交易計數與新增拒絕。
Router／transaction 單元測試涵蓋確認前後取消的名額回收，cyclic 單元測試驗證
取消 `stop()` 僅留下唯一停止命令。生命週期測試另驗證初次開啟延遲不觸發靜默重連。

這些自動測試與交叉編譯不能替代 Windows 原生 PCAN DLL／驅動及 PEAK 實機驗收。
涉及此執行邏輯的變更仍須保持 Draft PR，記錄受驗 SHA 並由實際驗收的維護者核准。
